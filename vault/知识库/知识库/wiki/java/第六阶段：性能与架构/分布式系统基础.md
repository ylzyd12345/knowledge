# 分布式系统基础

> CAP、BASE、分布式事务与一致性哈希。

本文建立分布式系统核心理论与常见方案全景。具体中间件实践见 Spring Cloud、消息中间件专题。

---

## 概念定义

**分布式系统**由多台独立计算机协同对外提供服务，通过网络通信，须面对网络分区、节点故障、时钟不一致等问题。

---

## 核心原理

### 1. CAP 定理

在网络分区（P）发生时，只能在 **一致性（C）** 与 **可用性（A）** 之间权衡：

- CP：强一致，可能拒绝服务（如 ZooKeeper 选举期间）
- AP：高可用，可能读到旧数据（如 Eureka）

实际系统多为 **PACELC**：分区时选 A 或 C；正常时选延迟 L 或一致 C。

### 2. BASE 理论

- **Basically Available**：基本可用
- **Soft state**：软状态，允许中间状态
- **Eventually consistent**：最终一致性

互联网业务常接受短暂不一致换取可用性与性能。

### 3. 分布式事务

| 方案 | 说明 |
|------|------|
| 2PC | 协调者两阶段提交，阻塞、单点 |
| TCC | Try-Confirm-Cancel，业务层实现 |
| 本地消息表 | 事务内写消息表，异步投递 |
| 事务消息 | MQ 半消息（RocketMQ） |
| Saga | 长事务拆为本地事务 + 补偿 |

Seata 提供 AT、TCC、Saga 等模式集成。

### 4. 一致性哈希

将 key 映射到环上节点，扩缩容只影响相邻区间，用于缓存分片、负载均衡。

### 5. 其他基础

- **幂等**：重复请求相同效果
- **限流**：令牌桶、漏桶、Sentinel
- **熔断降级**：故障传播隔离

---

## 实际应用

订单支付：本地事务扣库存 + 发 MQ → 积分服务消费（最终一致）。  
分库分表：用户 ID 取模或一致性哈希路由。

## 源码分析

一致性哈希在 Memcached 客户端、Redis Cluster slot 分配中应用。  
Raft/Paxos 是强一致复制的理论基础（etcd、Consul）。

## 面试常见题目

**1. CAP 如何理解？**

分区时 C 与 A 不能同时满足；多数系统选 AP + 最终一致。

**2. 分布式事务方案？**

2PC、TCC、消息最终一致、Seata AT。

**3. 如何保证接口幂等？**

唯一键、Token、状态机、去重表。

**4. 一致性哈希优点？**

扩缩容迁移数据量小。

**5. 脑裂问题？**

网络分区导致多主；须 quorum 与 fencing token。
